# Deployment acceptance

Automated tests cover business rules and console integration. These checks need actual Minecraft clients and your backend plugins; perform them on a staging proxy before production.

1. Join two different backends with two player accounts. Send `/g hello`; verify each participant sees exactly one message and the backend does not see a forwarded command.
2. Test ordinary chat with an older client and a signed modern client. For every acknowledged modern backend, install the matching SignedVelocity companion and verify one delivery, no backend duplicate, no kick, and no signed-chain warning after several messages and server switches.
3. Remove a server from `chat.signed-backends` and reload. Modern ordinary chat must stay backend-local; `/g` still works. Never acknowledge a backend without its companion.
4. Use staff send+receive, receive-only, and non-staff accounts. `/sc secret` must only reach staff receivers. Denied staff/private commands must not fall through to backend commands. Revoke receive permission and verify delivery stops immediately. Toggle `/sc` on, send ordinary chat, toggle it off, and verify staff messages never reach non-staff. Verify `/sc on` is refused on unsafe modern backends; while enabled, unsafe server switches must be blocked. Revoke sender permission while toggled and check the next ordinary message remains blocked.
5. Verify `/msg` and `/r` across servers, offline target handling, `/ignore`, `/msgtoggle`, disconnect/reconnect reply clearing, hidden permission lookup, and suggestions.
6. Verify routing groups, local chat, excluded servers, cooldowns, long/Unicode messages, and malicious formatting input. Check interactions with your moderation/vanish plugins.
7. Upgrade with customized chat and teleport text; verify it is imported into `language.properties`. Change a chat response there and reload; restart to verify changed teleport responses. Remove the old template lines from the settings files and confirm the wording stays the same. Reload a valid configuration, then an invalid one (including an unknown key in the language file). The latter must report an error and leave the previous routing active. Restart after changing aliases; inspect logs for command collisions.
8. Install PAPIProxyBridge on proxy/backends and PlaceholderAPI plus the prefix expansion on the backends. Use `{prefix}` and a raw `%placeholder%` in MiniMessage templates, verify sender-context prefixes across servers and private messages, then remove/unload a backend companion and verify bounded fallback instead of hanging delivery. Type MiniMessage/PAPI markup as a player and verify it remains literal. Exercise hover/click templates you choose to configure.
9. Test name completion in ordinary chat and message bodies with old and modern clients. Check cross-server joins, switches, disconnects, hidden players, and permission changes. On 1.13–1.19 clients inspect the legacy TAB additions and check interactions with your TAB/vanish plugins. Disable the fallback and verify only plugin-owned remote entries disappear.
10. Load-test at your expected concurrent players and message rate. Monitor proxy CPU, event timings, and outbound bandwidth; broadcast work grows with connected recipients. This release connects backend servers on a single proxy only.
# Network commands and backend teleports

Use a separate staging proxy and two Paper/Purpur 26.1.2 backends with your gameplay plugins.

1. Join from a real client while another is online. Both should see one join. Switch backends, then disconnect: switches must not announce, and the remaining player should see one leave. Repeat through an excluded authentication server and with hidden/see-hidden permissions. Use `announcements.debug=true` briefly if a recipient is missing.
2. Check `/whereami` after each switch. An ordinary player must be denied `/find` and `/tp`; proxy staff with the configured permissions can use them. Hidden players must be absent from denied lookups and suggestions.
3. Install the matching bridge on both backends with one private shared secret. With no/mismatched bridge on the target, `/tpa` acceptance must fail without changing the requester's server.
4. Request a same-server teleport and a cross-server teleport. Verify acceptance, denial, named acceptance of multiple requests, cancellation, expiry and cooldown. Confirm final world, coordinates and orientation, not just the server switch. Check staff `/tp` skips consent but requires its proxy permission.
5. Repeat with Inventory Sync enabled on both backends. The restored inventory must be ready before the location teleport. Interrupt database availability and verify no teleport bypasses the loading/failure gate. Test the bridge's `require-inventory-sync` setting with the inventory plugin absent/disabled.
6. Disconnect or switch the target during transfer, revoke permission, and cancel the teleport through your protection plugin. No success message should appear without a backend acknowledgment. A player already switched to the destination may remain at its spawn when location teleport fails.
7. Try an unauthorized client plugin message on `networkchat:teleport`: it must not be forwarded or accepted. Test world/server restrictions, stale replies, delayed chunk loads, plugin shutdown and restart. A late callback must not teleport after its signed expiry.

Automated tests cover these state transitions and server APIs with controlled player doubles. Real client/server transitions and third-party gameplay interactions require this staging run.
